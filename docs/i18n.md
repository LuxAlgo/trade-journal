# Trade Journal Internationalization (i18n) Behavior Contract

> Status: this document is the behavior contract for the seven-language i18n
> implementation. Update this document before adding user-visible copy, then change
> the code; stable product rules are maintained only here, while `tasks.md` records
> progress only. Locale identifiers and defaults follow the proposals adopted in
> `tasks.md` (T00) and can be changed later; all changes are centralized in
> `apps/web/src/i18n/config.ts`. Decisions confirmed on 2026-10-04.
>
> i18n in this document means UI internationalization: it affects only human-readable
> copy and display formatting. It never changes trade calculations, import parsing,
> authentication, or machine data contracts.

## 1. Locales and Identifiers

| Code  | Endonym  | Notes                                                   |
| ----- | -------- | ------------------------------------------------------- |
| en    | English  | Default locale, identical to the status quo, zero drift |
| zh-CN | 简体中文 |                                                         |
| ja    | 日本語   |                                                         |
| ko    | 한국어   |                                                         |
| zh-TW | 繁體中文 | zh-TW is the locale code for Traditional Chinese        |
| es    | Español  | UI code is `es`, region-neutral                         |
| fr    | Français | UI code is `fr`, region-neutral                         |

- Formatting mappings (BCP 47 identifiers for `Intl`): en→en-US, zh-CN→zh-CN,
  ja→ja-JP, ko→ko-KR, zh-TW→zh-TW, es→es-ES, fr→fr-FR. The mapping is exported from
  `apps/web/src/i18n/config.ts` and nowhere else.
- All seven languages cover: the web UI, AI responses (requests carry the locale
  explicitly), voice recognition (follows the UI language by default; the control can
  override it), and PDF/PNG review-export copy. No carve-outs.
- Switching entry point: a single place only, the "Settings → General" tab (narrowed
  by product decision (2026-10-04): the entries on the login page and in the app shell
  were removed to keep one entry point and avoid duplication). It uses the shared
  component `components/language-switcher.tsx`; languages render their own endonyms
  (`日本語`, `한국어`), never flags. The login page renders in the cookie/default
  language.
- Persistence: cookie Max-Age of 1 year.
- All seven languages are left-to-right (LTR); no `dir` attribute is set and no
  unverified RTL styling is pre-provisioned for future languages.

## 2. Language Selection and Switching Rules

- **Storage**: cookie name `NEXT_LOCALE` (the next-intl default), attributes
  `Path=/; SameSite=Lax; Max-Age=31536000; httpOnly=true`. `Secure` is deliberately
  not set: this project targets local self-hosted http, where a `Secure` cookie would
  not work.
- **Priority**: a valid cookie wins over the default `en`. A missing or invalid cookie
  (anything outside the seven-locale enum) is treated as the default `en`. The server
  accepts only enum members and never treats an arbitrary request string as a
  resource path. When the same request's Cookie header contains multiple
  `NEXT_LOCALE` values, the server uses the last occurrence (observed behavior).
- **First visit**: always the default language; no `Accept-Language` auto-detection.
  This keeps first-visit rendering identical across backend, frontend, and tests.
  After the user picks a language, the cookie decides.
- **Pre-login switching**: the UI no longer offers a pre-login entry point (see §1),
  but `/api/locale` remains a public endpoint (existing public paths in
  `middleware.ts` are `/login`, `/api/auth`, `/api/locale`). It only writes the
  language cookie, reads and writes no trade data, and grants no additional API
  permissions. Keeping it public makes it possible to restore a pre-login entry point
  later without touching the auth boundary.
- **URLs and query parameters**: no language in URLs and no `/zh-CN`-style path
  prefixes. Existing URLs (`/`, `/calendar`, `/trades`, ...) and filter query
  parameters stay as-is; bookmarks and external links are unaffected.
- **Across tabs**: the cookie is the source of truth. Server rendering picks the
  language from the request cookie; other tabs pick it up on their next reload. No
  cross-tab live broadcast.
- **SSR/CSR consistency**: one request, one source — the server selects messages from
  that request's cookie and injects the provider; client hydration consumes the same
  resources. The client must not decide the first-paint language from `localStorage`
  or `navigator.language`.
- **Switch behavior**: submit, wait for `/api/locale` to succeed, then
  `router.refresh()`. On failure, keep the old language and show an understandable
  error; never report the language as switched while the old one is still active.
  Switching never changes the current pathname, search params, or unsaved form
  content.

## 3. Message File Layout and Key Conventions

- Resource directory: `apps/web/messages/<locale>/<ns>.json` (e.g.
  `apps/web/messages/en/shell.json`). This supersedes the single-file
  `messages/{locale}.json` suggestion in the technical-route section of `tasks.md`:
  per-namespace files are what make parallel implementation without shared-file
  conflicts possible, since each namespace is created and owned by exactly one
  implementation group.
- The server loads only the selected namespaces for the current locale in
  `request.ts`; one language choice never loads all seven resource sets.
- Keys are camelCase; nesting stays within 3 levels; interpolation uses `{param}`;
  plurals use ICU plural (`{count, plural, one {...} other {...}}`).
- Shared semantics reuse keys (Delete / Cancel / Save live in `common`). Never use
  English copy as a key name. Never assemble sentences by concatenating fragments
  (express plurality and word order with complete messages). Translations must keep
  variable names intact — a parameter such as `{count}` must never be renamed,
  including translation into another language.
- The existing English UI is the semantic baseline for `en`; translations use the
  glossary in §15.
- **Workflow for new user-visible copy**: add `en` first, then complete the other six
  languages in the same batch. The resource-integrity gate
  (`scripts/check-messages.mjs` + a Vitest test, see §14) compares key sets across
  all seven resources; any missing language fails, and silent missing translations
  are not allowed.

## 5. Translation Scope and Exceptions

**Only product-controlled, user-visible UI copy is translated**, including:

- Buttons, headings, form labels, navigation, hints, empty states, loading states,
  disabled reasons;
- `aria-label`, `title`, `placeholder`, sr-only text, `role=status/alert` text;
- `window.alert`/`window.confirm` copy (bare `alert(`/`confirm(` global calls in
  code, behaviorally equivalent) — translate the strings first, keep the confirm
  behavior;
- Chart axis names, legends, tooltips; error messages; PDF/PNG review-export titles,
  headers/footers, and fixed labels.

**Never translated**:

- Brands: Trade Journal, LuxAlgo;
- Broker/exchange/market-data vendor names (Alpaca, OANDA, Tradezella, MetaTrader,
  NinjaTrader, IBKR, etc.) and AI model IDs;
- Account names, trade symbols, user notes/template bodies/custom strategy and rule
  names, historically AI-generated content;
- CSV column names and JSON keys, protocol fields (e.g. `{error}`, `code`,
  `status`), localStorage/cookie keys;
- Timezone IDs (e.g. `America/New_York`) and ISO currency codes (e.g. `USD`);
- Column-recognition keywords and format-detection labels of `packages/importers`
  (changing them would break import detection).

## 6. Visible API Error Strategy

- The English text of the server `{error}` field is a machine-stable identifier and
  **stays unchanged**. Existing consumers (including the regexes in
  `lib/ai-feedback.ts`, see §17.2) depend on the original text.
- Product-controlled high-frequency errors additionally carry a stable `code` field:
  a new field only; HTTP status and the semantics of the `error` field are unchanged,
  and existing tests such as `api-auth` are unaffected.
- **Server mechanics** (`server/api.ts`): `bad(message, status?, code?, params?)`
  returns `{ error, code?, params? }`; `RequestError(message, code?, params?)` and
  `requireValue(condition, message, code?, params?)` can carry code/params.
  `CodedError` is the base class that carries a code while preserving existing status
  semantics (the AI family uses it to keep 500). The handler funnels unknown
  or third-party exceptions into `internal_error`; a `RequestError` without a code
  keeps producing no `code` field (falling back to the English original). The 401
  JSON from `middleware.ts` carries `code: "unauthorized"` (text unchanged).
- **Client mechanics**: `lib/api-error.ts` defines `ApiError` (carrying
  `err.code`/`err.params`; `err.message` unchanged) and `formatApiError(t, err)` —
  when a code exists and the `errors` catalog has a matching key it returns
  `t('errors.<code>', params)`, otherwise it returns `err.message` as-is (no masking,
  no guessing). `formatApiError` accepts three input shapes: an `ApiError` instance,
  a plain object `{ message, code?, params? }` (the shape of `errorInfo` in
  `lib/use-api.ts`, which also carries the raw message as fallback text), and a plain
  string (returned as-is). `lib/use-api.ts` `postJson` and `lib/api-request.ts`
  `acquireJson` attach the response body's `code`/`params` to the thrown `ApiError`.
- **GET path (final implementation pass)**: beyond `error: string | null` (semantics
  unchanged, still the English original), `useApi` adds a non-breaking
  `errorInfo: { message, code?, params? } | null` — the code/params of an `ApiError`
  thrown by `acquireJson` no longer get lost when flattened to a string; failures
  without a code (network errors, un-encoded server errors) leave `errorInfo` null.
  Pages rendering user-visible errors localize with `formatApiError(t, errorInfo ??
error)` (falling back to `errorInfo.message`/the English original when no code
  matches); logs, debugging, and the raw text passed to `AiNotice` (which relies on
  English regex matching — see the prohibition below) stay original. `use-autosave`
  works the same way: its return value adds `saveState: { state, message, errorInfo }`;
  a failed save first localizes the detail through the `errors` namespace, then wraps
  it in `controls.autosave.notSaved` (`Not saved: {message}`) for rendering; the old
  `status` string is unchanged.
- The client localizes by looking `code` up in the `errors` namespace; a missing or
  unmatched code renders the English text as-is (no masking, no guessing). Long-tail
  validation errors (one-off field-level copy) get no code — that is the
  contract-sanctioned English fallback.
- **Never regex-match on the English body to decide UI translation.** The existing
  regexes in `lib/ai-feedback.ts` consume the server's English originals and remain
  valid; server text must not be rewritten to accommodate the UI.
- Third-party/unknown errors keep the existing safety boundary: present a localized
  summary plus a diagnosable `code`; never leak API keys, raw import content, or
  other sensitive data.

## 7. Importer Diagnostics Boundary

- The `warnings`/`errors` strings from `packages/importers` are English diagnostic
  originals; **they stay unchanged** and continue to be shown (developers can debug
  the original cause).
- Structured diagnostics (implemented):
  `ParsedImport.diagnostics?: Array<{code: string; params?: Record<string, string|number>}>`
  (`ImportDiagnostic`, `packages/importers/src/types.ts`). `app/api/import/route.ts`
  passes `diagnostics` through verbatim in preview and commit responses; commit
  appends `{code: "rows_skipped_journaled", params: {count}}` for skipped rows. The
  import page prefers localizing by `code` against the `import-diagnostics`
  namespace, falling back to the English original when missing (consumed by the
  import page, page group G).
- Per-item details of reconciliation conflicts (`server/ninjatrader-import.ts`,
  `server/position-import.ts`) remain English strings inside `ImportReview.conflicts`
  (that contract file is outside the error-mapping layer's scope and stays
  unchanged); when commit is blocked the response carries the stable
  `code: "import_reconciliation_conflict"` / `"import_position_conflict"`, and
  details fall back to the English original.
- European decimal ambiguity (silently resolved by `parseMoney`) and missing
  timezones (naive timestamps interpreted via the `timeZone` option) produce **no**
  warnings/errors in the current implementation, hence no diagnostic codes — no new
  behavior is added for them (detection/rejection rules unchanged).
- Detection/rejection rules, preview, and commit behavior are completely unchanged:
  switching languages must never change format-detection results, execution counts,
  amounts, import timestamps, or skip decisions.

## 8. Dates, Amounts, and Formatting Boundaries

- **Unchanged**: storage, filtering, import parsing, and CSV/JSON machine export
  formats never change. `YYYY-MM-DD` input/filter values, ISO timestamps, and the
  `en-CA` output of `lib/timezone.ts` `formatTimestamp` stay as-is. A trade's
  attribution timezone and the import timezone setting are fully independent of the
  UI language.
- **Rendered per locale**: human-readable month/weekday names, number thousand and
  decimal separators, and currency symbols are produced with `Intl` for the current
  locale.
- `lib/utils.ts` `fmtMoney`, `fmtNumber`, `fmtPercent`, `fmtDuration` gain a locale
  parameter, **defaulting to `en-US` for backward compatibility with existing call
  sites**; pages pass `useLocale()`. Cache keys include locale and currency/precision.
  Duration units such as `< 1m`, `h`, `d` become translatable messages.
- `lib/currencies.ts` `Intl.DisplayNames` (currently hardcoded `"en"`) produces
  currency names for the current locale, still keyed by ISO code.
- The `react-day-picker` calendar receives the matching date-fns locale. The week
  start day varies by locale, but **the financial week-statistics computation is
  unchanged** — only headers/display change; verify on the calendar page that
  trading-day attribution does not shift.
- Switching the language must never change account currencies, report aggregation,
  trading-day computation, or conversion results.

## 9. AI Language Boundary

- `ask`/`recap`/`critique` requests pass the verified UI locale explicitly, and the
  prompt instructs the model to respond in that language. Constraints based on actual
  trade data, length, cited numbers, and safe handling are preserved.
- Recap output keeps the first-person voice and the `**Keep**`/`**Fix**` structure,
  with the structure headings localized per language (the prompt explicitly requests
  the language-appropriate wording).
- AI import's JSON schema, fields, and time/fee extraction rules keep machine
  semantics; only its user-readable prompts/errors are translated.
- Historically AI-generated content is never rewritten or back-translated.

## 10. Voice Language Boundary

- Recognition language defaults to the UI locale's BCP 47 voice mapping: en→en-US,
  zh-CN→zh-CN, ja→ja-JP, ko→ko-KR, zh-TW→zh-TW, es→es-ES, fr→fr-FR.
- The `voice-note` control allows overriding the recognition language independently;
  the override applies only to that recognition session and never writes back to the
  UI language.
- When the browser does not support the selected language or speech recognition, show
  a clear error (reuse the localized copy for `lib/dictation.ts` errors such as
  `language-not-supported`); never fall back silently to English.
- During a language switch with an active recognition session: stop the old session
  and discard late-arriving results, so notes are never written in the wrong
  language.

## 11. PDF/PNG Review Export and Fonts

- Font per locale: en/es/fr → the existing NotoSans-Regular; zh-CN → NotoSansSC;

**Sentence-structure notes**:

- es: questions/exclamations use inverted `¿`/`¡`; spacing after colons matches en
  (one space); the es-ES formatting mapping uses `1.234,56` (dot thousands, comma
  decimals).
- fr: a non-breaking space precedes colons, `!`, `?`, `;`; the fr-FR formatting
  mapping uses `1 234,56` (space grouping, comma decimals); French copy runs about
  20-30% longer than en — watch buttons and narrow-viewport overflow. Always use the
  formal vous register (pronouns, verb forms, and imperatives all take vous forms),
  never tu; prompt instruction text sent to AI models is exempt.
- zh-CN/zh-TW: full-width punctuation (，。：；！？); half-width for digits and
  units; zh-CN uses 「」 and zh-TW uses 「」, while strings without quotes keep the
  source text's quoting; simplified/traditional vocabulary differences follow this
  table (e.g. 回撤/回檔, 复盘/複盤, and analogous 软件/軟體).
- ja: UI copy uses the polite です・ます register throughout; full-width punctuation
  (。、「」); no spaces around digits or Latin characters.
- ko: UI copy uses the formal 합니다 style throughout; hangul is written with word
  spacing (띄어쓰기); spaces between digits and units.
- Plural rules differ by language (zh/ja/ko have no singular/plural distinction and
  use `other`; en/es have only `one`/`other`; fr maps `0` and `1` to `one`) —
  express with ICU plural; never concatenate `s` by hand.

## 16. Rollback Path

- Code rollback: restore the previous code commit together with its
  dependency/resource versions (`pnpm-lock.yaml`, font assets included).
- No data migration: raw trade data carries no language fields; after rollback
  everything reads as before, and no language migration step is needed.
- A leftover `NEXT_LOCALE` cookie is harmless: older code does not read it.
- Real deployment rollbacks require checking the environment and authorization
  separately; they are out of scope for local work.

## 18. Acceptance Check: Does Switching the Language Change Business Results?

Under the boundaries in §6–§12, the answer to each is no:

1. **Import results unchanged**: importer detection/rejection rules, column-recognition
   keywords, and time/amount parsing are independent of the UI language (§7); language
   only decides whether diagnostic copy is localized by code or falls back to the
   English original (§7, §13).

## 19. Known Limitations and Maintenance Notes

This section records environment limitations left over from the seven-language
implementation (2026-10-04), implementation trade-offs, and wiring contracts that
future maintainers need. Everything here was verified at the time; re-validate if the
environment changes.

### 19.1 Manual next-intl Alias (Equivalent of `createNextIntlPlugin`)

next-intl 4.14.9 is used. The officially recommended
`createNextIntlPlugin("./src/i18n/request.ts")` failed to load in the implementation
environment (Windows): the Next compiler path depends on the `@swc/core` native
binding, which the local pnpm store could not provide there.
`apps/web/next.config.ts` therefore wires the equivalent by hand:
`turbopack.resolveAlias["next-intl/config"] = "./src/i18n/request.ts"` (relative
path) plus webpack `resolve.alias["next-intl/config"]` (absolute path) — the same
aliases the official plugin sets for Next 15.x. Behavior was verified identical by
SSR smoke tests and the test suite. To restore the official plugin: make `@swc/core`
load normally again (reinstall dependencies, possibly on another machine or with
Windows Developer Mode), then swap `next.config.ts` back to
`withNextIntl(createNextIntlPlugin("./src/i18n/request.ts"))` and delete the two
aliases. That is the only change involved.

### 19.2 Standalone Output and Symbolic Links on Windows

`pnpm build` compiles and generates all 47/47 static pages. On Windows machines
without Developer Mode/administrator rights, the standalone output step exits 1 with
EPERM when copying `node_modules` (symlinks for react and other pre-existing
dependencies). This is an environment limitation, not introduced by this change;
Docker/Linux deployment targets and CI (Linux checkouts) are unaffected.
`outputFileTracingIncludes` already tracks `./messages/**` (the seven language
directories) into the standalone output — messages are read from disk at request
time, and a missing directory would make every locale fall back with errors, so this
include must not be removed.

### 19.3 `pnpm-workspace.yaml` `allowBuilds` Trade-off

`@parcel/watcher` and `@swc/core` are set to `false`: both ship win32-x64 prebuilt
artifacts, and skipping their build scripts avoids install failures on machines
without an MSVC toolchain. `esbuild` and `better-sqlite3` stay `true` (they need, or
already have, a working build path). Re-evaluate when moving to a platform without
prebuilt artifacts.

### 19.4 GET Error Path: `errorInfo` and `formatApiError`

The server error contract stays `{ error, code?, params? }`: `error` is the
machine-stable English original (existing consumers such as `lib/ai-feedback.ts`
match on it verbatim and it must not be rewritten), `code` points to a key in the
`errors` namespace, and `params` feeds that key's ICU placeholders. On the client,
`lib/api-error.ts` defines `ApiErrorInfo` (`{ message, code?, params? }`) and
`formatApiError(t, error)`: it localizes by looking the code up in the `errors`
catalog and falls back to the original when there is no code or no entry, without
translating the fallback a second time (§6). `lib/use-api.ts` exposes GET failures as
the `errorInfo` shape so pages can hand them straight to `formatApiError`. When
wiring GET error display on a new page: take `errorInfo` → the `t` from
`useTranslations("errors")` → `formatApiError(t, errorInfo)`, and never regex-match
on the `error` original.

### 19.5 `use-autosave`: `saveState` and `formatAutosaveStatus`

`lib/use-autosave.ts` maintains `AutosaveState` (idle/saving/saved/error + message +
errorInfo). `formatAutosaveStatus(tControls, tErrors, saveState, fallback)` (4 args)
renders the autosave state in the current language: in the error state it first
localizes via `formatApiError(tErrors, saveState.errorInfo)` by code and wraps it
with `tControls("autosave.notSaved")`; idle returns the fallback. New pages wiring
autosave consume the same pair of primitives (the `saveState` returned by
`use-autosave` + `formatAutosaveStatus`), so save failures stay readable and never
falsely report success in all seven languages; re-rendering after a language switch
naturally brings the new language's copy, with no stale cached translations.

### 19.7 Rollback Path

Restoring the previous code version together with its dependency/resource versions
rolls back the entire i18n change (see §16): no data migration; SQLite data, export
files, and the language cookie keep reading under the original contract after
rollback; the language cookie is ignored by the older version and needs no cleanup.
Any real deployment rollback additionally requires checking the environment and
authorization.
